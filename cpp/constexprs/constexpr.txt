Вся идея крутится вокруг того когда поставить значение в рантайме или компайл тайме


const говорит что объект меняться не будет но его значение можно получить в рантайме
    const int x = getValue();

constexpr константное значение (менять нельзя) с c++11 значение обязано быть вычисленно на этапе компиляции и автоматически делается const 
    тип обязан быть литеральным
    constexpr int n = 5 * 5;
    constexpr n = getValue(); // error 

if constexpr c++17 это compile-time ветвление, в основном в шаблонах. Невыбранная ветка отбрасывается (не инстанцируется), поэтому она не обязана быть валидной для данного типа:
    template<typename T>
auto deref(T t) {
    if constexpr (std::is_pointer_v<T>)
        return *t;     // инстанцируется только для указателей
    else
        return t;
}

consteval c++20 до него функцию с constexpr можно было посчитать в рантайме и компайл тайме
    constexpr 

    constexpr int square(int v) {return v * v;}
    int r = square(5); // ok

    consteval int square(int v) { return v * v;}
    int r = square(5); // error 

constinit against static initialiazation order fiasco применяется к static/thread storage duration 
    гарантирует конст инициализацию на этапе компиляции до любой динамической но const там нет менять можно
    Проблема Глобальные объекты из разных translation unit, требующие динамической инициализации, инициализируются в неопределённом порядке. 
    А constinit заставляет компилятор инициализировать переменные статически поэтому она точно готова к моменту динамического кода 

Динамическая инициализация — это инициализация объекта со static storage duration (глобального, namespace-scope, static-переменной), 
оторая требует выполнения кода в рантайме, потому что начальное значение нельзя посчитать на этапе компиляции.


Ключевое правило порядка: вся статическая инициализация происходит ДО любой динамической. А вот сама динамическая упорядочена лишь частично — внутри одного translation unit в порядке определения, 
но между разными TU порядок не определён. 
то и есть корень static initialization order fiasco, про который я писал в контексте constinit:

// file1.cpp
Foo globalFoo = makeFoo();        // dynamic init

// file2.cpp
extern Foo globalFoo;
int globalBar = globalFoo.value(); // dynamic init, ИСПОЛЬЗУЕТ globalFoo

Если динамическая инициализация file2.cpp случится раньше file1.cpp, то globalBar прочитает ещё не сконструированный globalFoo → UB. 
Компилятор не обязан выбирать «правильный» порядок, потому что между TU он не специфицирован.

constexpr = (почти) constinit + const 

запуск .exe
   │
   ├─ [startup]  динамическая инициализация глобалов   ← до main(), фиаско живёт тут
   │
   ├─ main() стартует   (в Qt: QApplication app; ... app.exec();)
   │
   ├─ event loop крутится
   │
   └─ клик кнопки → openTrainDialog() → твои вычисления  ← ТОЖЕ рантайм, просто позже
