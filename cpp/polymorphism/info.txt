// CRTP — "статические виртуальные функции"
template <class Derived>
struct Shape {
    double area() const {
        return static_cast<const Derived*>(this)->area_impl();
    }
};

struct Circle : Shape<Circle> {
    double r;
    double area_impl() const { return 3.14159 * r * r; }
};

CRTP 
    Curiously Recurring Template Pattern
    "Любопытно повторяющийся шаблон"
    шаблонный базовый класс, который принимает производный класс в качестве параметра шаблона
    
template <class Derived>
struct Base { /* ... */ };

struct Foo : Base<Foo> { /* ... */ };   // вот это оно
//           ^^^^^^^^^^ Foo передаёт сам себя как параметр

Статический полиморфизм — это когда «какая функция вызовется» решается на этапе компиляции, а не в рантайме. Никакой vtable, 
никакого виртуального вызова: компилятор подставляет конкретный код под конкретный тип. 
Отсюда и плюсы (инлайнинг, ноль оверхеда), и минусы (тип должен быть известен в compile-time, нельзя просто сложить разные типы в один контейнер, как с Base*).


template <typename T>
void render(const T& shape) {
    shape.draw();   // подойдёт любой T, у которого есть draw()
}

struct Circle { void draw() const { /* ... */ } };
struct Square { void draw() const { /* ... */ } };

render(Circle{});  // компилятор инстанцирует render<Circle>
render(Square{});  // и render<Square>

Главная развилка одна: известен ли конкретный тип на этапе компиляции. Если решение о типе принимается в рантайме — статика физически не может, вопрос закрыт. Всё остальное — это уже тонкая настройка внутри «известно в compile-time».

Бери динамический (виртуальные функции), когда:

Тип выбирается в рантайме. Классика — фабрика, которая по расширению файла или настройке решает, что создать. У тебя же ровно такой случай с ISpreadsheetIO: пользователь выбрал XLSX или CSV, и ты хочешь дальше работать через один интерфейс, не зная конкретного класса. Шаблоном это не выразить — тип неизвестен в точке, где ты пишешь код.

Нужны разнородные объекты в одном контейнере — vector<unique_ptr<Base>>. Хочешь загружать плагины, подменять реализацию, инжектить моки в тестах. Всё это — про то, что связь «вызов → реализация» устанавливается позже компиляции.

Хочешь спрятать реализацию за стабильной границей: pimpl, стабильный ABI библиотеки, разрыв зависимостей между модулями. Виртуальный интерфейс живёт в заголовке в паре строк, реализация — в .cpp, и она не течёт наружу. Плюс это режет время компиляции — потребителю интерфейса не нужно видеть кишки.

Бери статический (шаблоны/CRTP), когда:

Тип известен на сборке, и это горячий путь, где важен инлайнинг и ноль оверхеда. Виртуальный вызов сам по себе дёшев, но он ставит барьер оптимизатору — компилятор не может заинлайнить то, что резолвится через vtable. На внутреннем цикле обработки данных (твои HostMatrix/CUDA-штуки) это может быть заметно; на клике по кнопке в Qt — абсолютно всё равно.
