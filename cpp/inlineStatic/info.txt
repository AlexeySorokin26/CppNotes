Основа 
    Компилятор обрабатывает программу по одному cpp за раз. Каждый cpp после препроцесосора это один TU. 
    Пока компилятор работает над widget.cpp он ничего не знает про dialog.cpp. Связать их работа линкера. 
    Линкер связывает их по именам символов
    Символ (symbol) — это именованная сущность, которую линкер отслеживает между объектными файлами. 
    Грубо: каждая функция и каждая глобальная/статическая переменная, у которой есть linkage, превращается в символ в .o-файле. 
    Символ — это запись в таблице вида «имя → что это / где это».
    Name Mangling искажение имен
        компилятор запекает в имя символа дополнительную инфу namespace function name argument types class claficators
            строка перестает быть просто helper  

    Расшифрую тот пример по кусочкам — _ZN3gui6helperEi:

        _Z — префикс «это mangled-имя C++»;
        N ... E — скобки вокруг квалифицированного (вложенного) имени;
        3gui — идентификатор с длиной впереди: 3 символа, gui;
        6helper — 6 символов, helper;
        после E идут типы аргументов: i = int (d был бы double, v — void/без аргументов).        
        Складываем → gui::helper(int).
        Mangling можно выключить — extern "C".


    У каждого имени есть linkage 
        internal linkage имя видимо внутри своего TU. Линкер его не экспортирует. Другие TU про него не знают.  
        external linkage имя видно всем TU
        по умолчанию свободная функция имеет external linkage

    ODR ограничение из-за которого нужны static и inline
    ODR символ с external linkage должен иметь ровно одно опеределение на всю програму

Проблема №1 — одинаковые имена в разных TU:
    cpp// widget.cpp
    void helper() { /* версия для виджета */ }   // external

    // dialog.cpp
    void helper() { /* версия для диалога */ }    // external

Проблема №2 — определение в заголовке:
    // utils.h
    int square(int x) { return x * x; }   // external

Заголовок включён в widget.cpp и в dialog.cpp. 
После препроцессора определение square физически лежит в обоих TU → два определения одного external-символа → опять ошибка линковки.

static linkage internal; linker does not see it ; живет в одном TU у каждого своя копия
inline linkage external; linker see it          ; одна копия на всех  

static решает проблему №1: делает символ internal
static перед свободной функцией = «дай ей internal linkage, не показывай линкеру».

// widget.cpp
static void helper() { /* ... */ }   // internal — линкер не видит

// dialog.cpp
static void helper() { /* ... */ }   // internal — другой, независимый
Конфликта нет: оба невидимы за пределами своего TU, линкер про них даже не знает. Каждый живёт в одном TU.
Бонус: компилятор видит все вызовы внутри TU (снаружи никто не дёрнет), поэтому часто полностью встраивает и отдельную функцию вообще не emit'ит.

inline решает проблему №2: разрешает дубликаты и мержит их
inline не делает символ internal. Символ остаётся external. 
inline говорит линкеру: «у этого external-символа может быть несколько одинаковых определений в разных TU — это не ошибка, выбери одно».

// в заголовке, включённом в 3 TU:

inline int next() { static int n = 0; return ++n; }
// ОДИН n на всю программу (символ смержен).
// next() из любого TU: 1, 2, 3, 4...

static int next() { static int n = 0; return ++n; }
// internal → в каждом TU СВОЯ копия next и СВОЙ n.
// 3 независимых счётчика. Почти всегда баг.


static → internal linkage → функция приватна своему TU. В .cpp это одна копия; десяток — только при ошибочном помещении в заголовок. 
    Смысл: спрятать деталь реализации одного .cpp (и заодно снять риск коллизии). Эквивалент — анонимный namespace, но не именованный.
inline → external linkage → определение в заголовке размножается по TU (тут десяток копий — норма), и линкер схлопывает их в одну. 
    Корректно лишь потому, что копии обязаны быть идентичны

static на свободной функции в cpp файле прячет эту функцию в этом TU


namespace TextStyle {

const QString colorError = "#FA4141";   // Red for errors
const QString colorWarning = "#FFA500"; // Orange for warning
const QString colorSuccess = "#32CD32"; // Green for success
const QString colorInfo = "#00BFFF";    // Blue for progress and user actions

// Helper function to wrap text in a colored HTML span.
inline QString Styled(const QString& text, const QString& color) {
    return QString("<span style=\"color:%1;\">%2</span>").arg(color, text);
}

} // namespace TextStyle

что происходит это хедер мы будем его инклюдить в разные Translation unit получается 
мы нарушим ODR функции по умолчанию external linkage

inline говорит линкеру «эти определения гарантированно идентичны — оставь одно, остальные выкинь».
На выходе — одна сущность, один адрес, external linkage. 

static на namespace/file scope — это внутренняя линковка. 
каждый TU получает свою отдельную копию функции: N сущностей, N адресов. 
ODR не нарушается, потому что имена приватные для своего TU и не сталкиваются.
Минусы — раздувание кода (N копий) и тот же static-локал был бы свой в каждом TU (вот где скрытый баг).

Для переменных — ровно тот же паттерн
inline-переменная (C++17) → один общий объект на программу, один адрес, external linkage. 
static-переменная на namespace scope → своя копия в каждом TU.

Когда что: inline — для header-only утилит, которые должны быть общими (твой Styled, твои цвета). 
static (или анонимный namespace, что современнее) — когда что-то должно быть намеренно приватным для одного TU и не светиться наружу.

extern говорит что переменная определена где-то в другом месте 
переменные как и функции по умолчанию имеют external linkage

Объявление (Declaration): extern int uno; — это объявление, а не определение. Вы говорите компилятору: «Эта переменная типа int с именем uno существует, но её память выделена в другом .cpp файле. Поверь мне, линковщик найдёт её».

Определение (Definition): extern int uno = 5; — это определение (инициализация перебивает extern). В этом случае вы сами создаёте переменную.
