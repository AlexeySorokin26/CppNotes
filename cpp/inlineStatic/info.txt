# Linkage, TU, ODR — конспект

## 1. Translation Unit (TU)

Компилятор обрабатывает программу по одному `.cpp` за раз. Каждый `.cpp` после препроцессора — это один TU.

Пока компилятор работает над `widget.cpp`, он ничего не знает про `dialog.cpp`. Связать их — работа **линкера**.

## 2. Символы

Линкер связывает TU по именам символов.

- **Символ (symbol)** — именованная сущность, которую линкер отслеживает между объектными файлами.
- Грубо: каждая функция и каждая глобальная/статическая переменная с linkage превращается в символ в `.o`-файле.
- Символ — запись в таблице вида «имя → что это / где это».

### Name Mangling (искажение имён)

Компилятор запекает в имя символа доп. инфу: namespace, имя функции, типы аргументов, class-квалификаторы. Строка перестаёт быть просто `helper`.

Разбор примера `_ZN3gui6helperEi`:

| Кусок | Значение |
|---|---|
| `_Z` | префикс «это mangled-имя C++» |
| `N ... E` | скобки вокруг квалифицированного (вложенного) имени |
| `3gui` | длина + строка: 3 символа → `gui` |
| `6helper` | 6 символов → `helper` |
| `i` (после `E`) | тип аргумента: `int` (`d` — double, `v` — void/без аргументов) |

Итого: `gui::helper(int)`.

Mangling можно выключить — `extern "C"`.

## 3. Linkage

У каждого имени есть linkage:

- **internal linkage** — имя видимо только внутри своего TU, линкер его не экспортирует, другие TU про него не знают.
- **external linkage** — имя видно всем TU.
- По умолчанию свободная функция имеет external linkage.

## 4. ODR (One Definition Rule)

Символ с external linkage должен иметь **ровно одно** определение на всю программу.

### Проблема №1 — одинаковые имена в разных TU

```cpp
// widget.cpp
void helper() { /* версия для виджета */ }   // external

// dialog.cpp
void helper() { /* версия для диалога */ }   // external
```
→ два разных определения одного external-символа `helper` → ошибка линковки.

### Проблема №2 — определение в заголовке

```cpp
// utils.h
int square(int x) { return x * x; }   // external
```
Заголовок инклюдится в `widget.cpp` и в `dialog.cpp`. После препроцессора определение `square` физически лежит в обоих TU → два определения одного external-символа → снова ошибка линковки.

## 5. static vs inline — коротко

| | linkage | что видит линкер | копии |
|---|---|---|---|
| `static` | internal | не видит символ вообще | своя копия в каждом TU |
| `inline` | external | видит, но разрешает дубликаты-определения | одна копия на всю программу (мержится) |

### `static` решает проблему №1: делает символ internal

`static` перед свободной функцией = «дай ей internal linkage, не показывай линкеру».

`inline` тут не поможет: `inline` говорит компилятору «выбери одно определение из нескольких одинаковых», 
а не «спрячь символ от линкера». 
А у нас разные функции с разными телами — значит `inline` не спасёт, конфликт всё равно будет.

```cpp
// widget.cpp
static void helper() { /* ... */ }   // internal — линкер не видит

// dialog.cpp
static void helper() { /* ... */ }   // internal — другой, независимый
```
Конфликта нет: оба невидимы за пределами своего TU, линкер про них даже не знает.

Бонус: компилятор видит все вызовы `helper` внутри TU (снаружи её никто не дёрнет), 
поэтому часто полностью инлайнит вызовы и отдельный символ вообще не эмитит.

### `inline` решает проблему №2: разрешает дубликаты и мержит их

`inline` **не** делает символ internal — он остаётся external. 
`inline` говорит линкеру: «у этого external-символа может быть несколько *идентичных* определений в разных TU 
— это не ошибка, оставь одно».

```cpp
// в заголовке, включённом в 3 TU:

inline int next() { static int n = 0; return ++n; }
// ОДИН n на всю программу (символ смержен).
// next() из любого TU: 1, 2, 3, 4...

static int next() { static int n = 0; return ++n; }
// internal → в каждом TU СВОЯ копия next и СВОЙ n.
// 3 независимых счётчика. Почти всегда баг.
```

### Итог по функциям

- **`static`** → internal linkage → функция приватна своему TU. В одном `.cpp` — это одна копия; десяток копий возникает только при ошибочном помещении в заголовок.
  Смысл: спрятать деталь реализации одного `.cpp` (и заодно снять риск коллизии имён). 
  Более современный эквивалент — анонимный namespace.
- **`inline`** → external linkage → определение в заголовке размножается по TU (тут десяток копий — норма), и 
линкер схлопывает их в одну.
  Корректно только потому, что копии обязаны быть идентичны.

## 6. Пример: почему в заголовке нужен `inline`

```cpp
namespace TextStyle {

const QString colorError = "#FA4141";
const QString colorWarning = "#FFA500";
const QString colorSuccess = "#32CD32";
const QString colorInfo = "#00BFFF";

// Helper function to wrap text in a colored HTML span.
inline QString Styled(const QString& text, const QString& color) {
    return QString("<span style=\"color:%1;\">%2</span>").arg(color, text);
}

} // namespace TextStyle
```

Этот хедер будет инклюдиться в разные TU. Функция по умолчанию имеет external linkage → без `inline` 
мы бы нарушили ODR (несколько определений одного external-символа в разных TU).

`inline` говорит линкеру: «эти определения гарантированно идентичны — оставь одно, остальные выкинь». 
На выходе — одна сущность, один адрес, external linkage.

**Что было бы со `static` вместо `inline` здесь:**
`static` на namespace/file scope — это internal linkage. 
Каждый TU получил бы свою отдельную копию `Styled`: N сущностей, N адресов. 
ODR формально не нарушается (имена приватные для своего TU и не сталкиваются), но:
- раздувание кода (N копий функции);
- если бы внутри был `static`-локал (как `static int n` в примере с `next()` выше) — в каждом TU была бы своя, независимая копия этой переменной. Скрытый баг.

**Тот же паттерн для переменных:**
- `inline`-переменная (C++17) → один общий объект на программу, один адрес, external linkage.
- `static`-переменная на namespace scope → своя копия в каждом TU.

**Когда что использовать:**
- `inline` — для header-only утилит, которые должны быть общими (твой `Styled`, твои цвета).
- `static` (или анонимный namespace, что современнее) — когда что-то должно быть намеренно приватным для одного TU и не светиться наружу.

## 7. `extern`

Переменные, как и функции, **по умолчанию имеют external linkage**. Единственное исключение — `const`/`constexpr` на namespace scope, у них по умолчанию internal linkage (исторический C++-специфичный нюанс, в C такого нет):

```cpp
int uno = 5;         // external linkage (по умолчанию) — определение
const int dos = 5;   // internal linkage (по умолчанию!) — тоже определение
```

`extern` говорит, что переменная определена где-то в другом месте. Важно не путать **linkage** и **определение/объявление** — это два разных вопроса:

- **Объявление (declaration):** `extern int uno;` — не определение, памяти не выделяет. Вы говорите компилятору: «переменная типа `int` с именем `uno` существует, её память выделена в другом `.cpp` файле — линковщик найдёт её».
- **Определение (definition):** `extern int uno = 5;` — это определение (инициализация перебивает `extern`). В этом случае вы сами создаёте переменную.

`extern` **не меняет linkage** переменной (она и так external по умолчанию) — он меняет конкретное вхождение из определения в чистое объявление:

```cpp
int uno;          // определение: выделяет память под uno прямо здесь
extern int uno;   // только объявление: памяти не резервирует, доверяет линкеру найти определение в другом TU
```

Отсюда стандартный паттерн для глобальной переменной, шаренной между несколькими `.cpp`:

```cpp
// globals.h
extern int uno;      // объявление — можно инклюдить в сколько угодно TU, конфликта нет

// globals.cpp
int uno = 5;          // единственное определение — ровно в одном .cpp
```

Если бы в хедере было `int uno;` **без** `extern`, а хедер инклюдился бы в несколько `.cpp` — получилось бы N определений одного external-символа `uno` → нарушение ODR, ошибка линковки. Ровно та же проблема №2, что и с `square()` выше, только для переменной вместо функции.

## 8. Способы получить internal linkage

`static int a;` — плохой пример, у слова `static` слишком много значений:

1. internal linkage (namespace/file scope) — этот случай;
2. статическая переменная внутри функции;
3. статический метод класса;
4. статическое поле класса.

Более однозначные способы:

```cpp
const int a = 10;   // const на namespace scope в C++ по умолчанию internal linkage

namespace {
    int a;
}
```

Анонимный namespace — компилятор генерирует ему уникальное имя, что-то вроде:

```cpp
namespace @uniqueName {
    int a;
}
```

Так переменная закрыта от всего остального кода: имя уникально для каждого TU, снаружи недоступно.

## Ответ на TODO: «чем static полезнее inline»

Это не вопрос «что лучше», а вопрос **разного назначения**:

- **`static`** полезен, когда тебе нужна *приватность* — деталь реализации одного `.cpp`, которая не должна быть видна и доступна другим TU (и линкеру). Побочный эффект — компилятор агрессивнее инлайнит вызовы внутри TU, потому что точно знает все места использования.
- **`inline`** полезен, когда тебе, наоборот, нужна *общность* — одна и та же сущность (функция/переменная), физически описанная в header, должна существовать в единственном экземпляре на всю программу, несмотря на то что текст попадает в N `.cpp` файлов.

Если попытаться использовать `static` там, где нужен `inline` (header-only утилиты) — получишь N независимых копий и N независимых `static`-локалов внутри них (баг вроде отдельного счётчика в каждом TU).

Если попытаться использовать `inline` там, где нужен `static` (приватная реализация в `.cpp`) — просто не тот инструмент: `inline` не скрывает символ от линкера, поэтому не решает задачу «спрятать `helper()` от других TU», ведь у тебя реально *разные* функции с одинаковым именем, а не идентичные копии одной.

Короче: `static` — про **видимость** (спрятать), `inline` — про **дедупликацию идентичных определений** (не спрятать, а безопасно размножить и потом схлопнуть).
